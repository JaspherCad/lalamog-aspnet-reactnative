# RabbitMQ and durable background workflows

Status: **RabbitMQ provisioned only; no application integration**. Audited 2026-10-28. BE-04 / FE-05 own implementation.

## Current evidence

`compose.yaml` runs a pinned RabbitMQ image with management UI, persistent `rabbitmq-data`, loopback ports 5672/15672, and credentials generated by `scripts/setup.ps1`. The API project has no RabbitMQ client package, publisher, queue topology, consumer, or outbox. `/health` currently checks SQL only. A healthy broker does not prove any feature uses it.

Redis is similarly provisioned but unused; it is not an implicit queue/cache/backplane dependency.

## First concrete workflow (planned)

Durable **in-app session notifications** for proposal, confirmation, cancellation, and completion. Keep matching/chat/session writes synchronous in SQL; RabbitMQ handles follow-up delivery. No email/SMS provider, paid service, or external messaging is required for this first slice.

Planned flow:

1. Domain transaction writes session change plus outbox event atomically in SQL.
2. Dispatcher publishes a versioned event with stable EventId/correlation ID using publisher confirms. Mark publication only after confirmation; ambiguous outcomes may publish twice.
3. Durable queue consumer processes with bounded concurrency and records event deduplication plus participant-scoped notification in SQL. Acknowledge after committed processing.
4. Retry transient failures with backoff and a finite limit. Poison messages go to dead-letter storage/queue with safe diagnostics and an explicit replay path.
5. Frontend reads durable notifications; optional SignalR only wakes a refetch. Reconnect/reload obtains unread state from SQL.

Delivery is at least once; consumers must be idempotent. Publisher confirms and consumer acknowledgements cover different legs of delivery; neither alone proves end-to-end processing. See [RabbitMQ confirmation documentation](https://www.rabbitmq.com/docs/confirms) (checked 2026-10-28).

Topology names, event DTOs, client library version, configuration keys, worker hosting, and notification routes are still design work. Record the implemented choices here and in API/schema docs once verified; avoid speculative endpoints in callers.

## Rules

- No broker/network call inside the retriable domain transaction. An unavailable broker must not discard accepted SQL changes or silently lose follow-up work.
- Events carry IDs and minimal state; no emergency contacts, passwords, chat bodies, email addresses, or precise private coordinates.
- Broker credentials stay server-side. No browser connection to RabbitMQ or management API.
- Keep schema version, deduplication retention, ordering strategy per session, and replay behavior explicit. Process replayed events without duplicate notification side effects.
- Observe outbox age/count, failures/retries, dead letters, processing lag, and worker readiness without logging private payloads.

## Recovery and acceptance

Until BE-04 is implemented, a broker outage has no expected application-level effect; do not diagnose existing chat issues as RabbitMQ issues. After integration, inspect SQL outbox/inbox/notification state, confirmed publish tracking, worker logs and queue depth before replaying anything. Preserve queue and SQL volumes.

Required tests: broker down during session mutation → SQL/outbox committed → broker restart → eventual notification; publish-confirm ambiguity → redelivery without duplicate effect; consumer crash before/after commit → correct retry; poison event → bounded retries/dead letter; replay → no duplicate; unauthorized users cannot read notification data. Use real local RabbitMQ and isolated test topology. Add outbox/Blob dependencies to health/readiness only with explicit liveness versus readiness behavior.
